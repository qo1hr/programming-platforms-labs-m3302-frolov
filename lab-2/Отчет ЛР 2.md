# Лабораторная работа 2. Анализ объектных файлов и исправление hotfix

Среда: Linux x86-64, GCC 14.2.0, GNU binutils 2.44 (контейнер Alpine).

## Этап 0. Размеры

Вывод `size core.o legacy.o hotfix.o main.o`:

```text
   text   data    bss    dec    hex filename
    266   4040  50000  54306   d422 core.o
    172      0      4    176     b0 legacy.o
    127      0      0    127     7f hotfix.o
    118      0      0    118     76 main.o
```

Аномальный BSS у `core.o` создаёт `large_buffer` размером `0xc350` = 50 000 байт (`nm -S`). `.bss` имеет тип `NOBITS`: в файле хранится требуемый размер, а память выделяется и обнуляется загрузчиком.

## Этап 1. Секции и строки

`readelf -SW core.o` показывает точное имя секции строк: `.rodata` (`PROGBITS`, размер `0x4c`). `strings -a core.o` находит `System Initialized v1.0`, `%s, Mode: %d` и секретный токен `FLAG{b1nary_4rch4eology_2026}`.

## Этап 2. Символы

Общее имя в таблицах четырёх модулей — `system_mode`:

| Файл | `nm` | `readelf` Ndx | Значение |
|---|---|---|---|
| `core.o` | `D` | `3` (`.data`) | Сильное инициализированное определение, 4 байта |
| `legacy.o` | `C` | `COM` | COMMON-символ, 4 байта |
| `hotfix.o` | `C` | `COM` | COMMON-символ, 4 байта |

`main.o` не определяет `system_mode`; его `U` ссылки — `apply_hotfix` и `print_status`. В исходном варианте `hotfix.c` строка `char system_mode[4];` создаёт tentative definition, которое при `-fcommon` попадает в COMMON. В `core.o` уже есть определение в `.data`, поэтому несколько модулей претендуют на один глобальный объект.

## Этап 3. Компоновка

`gcc -fcommon core.o legacy.o hotfix.o main.o -o app` завершилась с кодом 0 без ошибок и предупреждений. Флаг при **компоновке** не меняет типы уже собранных `.o`; линкер разрешил COMMON через сильное определение из `core.o`. Программа `app` запускается.

## Этап 4. Итоговый символ и фикс

`nm app | grep system_mode`:

```text
0000000000004020 D system_mode
```

Символ находится в `.data`, поскольку линкер выбрал сильное определение из `core.o`.

Команда из задания `gcc -fno-common main.o hotfix.o legacy.o core.o -o app_better` **тоже успешно завершается**: `-fno-common` при линковке не пересобирает старый `hotfix.o`. Чтобы получить обещанную ошибку, исходный `hotfix_original.c` был пересобран:

```sh
gcc -fno-common -c hotfix_original.c -o hotfix_nocommon.o
gcc main.o hotfix_nocommon.o legacy.o core.o -o app_conflict
```

Существенная строка диагностики:

```text
core.o:(.data+0x0): multiple definition of `system_mode'; hotfix_nocommon.o:(.bss+0x0): first defined here
collect2: error: ld returned 1 exit status
```

Исправленный `hotfix.c` содержит только объявление чужой переменной и реализацию функции:

```c
extern char system_mode[4];

void apply_hotfix(void) {
    system_mode[0] = 'A';
    system_mode[1] = 'B';
    system_mode[2] = 'C';
    system_mode[3] = '\0';
}
```

Проверка:

```sh
gcc -fno-common -c hotfix.c -o hotfix_fixed.o
gcc main.o hotfix_fixed.o legacy.o core.o -o app_better
nm app_better | grep system_mode
./app_better
```

`hotfix_fixed.o` содержит `U system_mode`, компоновка прошла с кодом 0, а в `app_better` сохранился единственный символ `D system_mode`. Программа запускается.
